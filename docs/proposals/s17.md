# s17 — park stats (attractiveness, leisure, coverage, upkeep) as the last thing to configure

Research and formulas: `docs/PARK-STATS.md`. All contract changes are additive.

## Contract changes (lead, please review)

Core
- `Core/Composition.cs` `Recipe.ParkStats` (`Build.ParkStatsSettings`, null = suggested values); `Recipe.Clone` copies it.
  Not in recipe JSON, presets or the "modified" fingerprint: it is per build.
- New `Core/Build/ParkStats.cs`: `ParkStatIds` (save-format ids: attractiveness, leisure, coverageRange,
  coverageCapacity, entertainment, upkeep; `attractiveness.inGame` for the value set on the lot), `ParkStatsKind`,
  `ParkStatsSettings` {KeepVanilla = true, Overrides}, `ParkStatsRecord`, `ParkStatsInput.From(plan, areaM2, recipe)`,
  `ParkStatsEstimator.Estimate/Band/Comparables`, `ParkStatsResult`.
- New `Core/Build/VanillaParks.cs`: 52 vanilla park prefabs with their real component values.
- `GroupRecord.ParkStats` + `ReceiptCodec` **v2**: one length-framed block appended after the area block
  (keepVanilla, overrides, applied values, kind, leisure type). Decode puts the settings back on `Recipe.ParkStats`
  so Edit keeps them. v1 receipts decode unchanged; v1 readers ignore the extra block.
- `PROTOCOL` / `UiModels.Protocol` bumped to 17 (master: 16) (new summary field + triggers).
- `UiModels.SummaryInput.AreaM2`; `UiModels.Summary` adds `parkStats` when the recipe is a park type;
  `UiModels.ParkStats(result)`.

UI (`contract.ts`)
- `Summary.parkStats?: ParkStatsView` (`ParkStatView`, `ParkStatId`).
- Triggers `setParkStat(id, valueJson)`, `resetParkStat(id | "")`, `setParkStatsKeepVanilla(bool)`.
  Undoable, never re-plan (they bump only the design version and `ParkStatsVersion`).

Game
- `BuildService.FinishParkStats` (FinishRecord): stats into the receipt, "Attractiveness" into the record stats, vanilla
  `AttractivenessProvider` on the owner lot (× terrain bonus). Setting `ApplyParkStats` (default on).
- `GroupRegistrySystem.SyncParkStats` after load (restore / remove per setting).
- `ToolRegistration.SettingsLocale` now also maps the build options that had Lang keys but no mapping
  (ClearExistingTreesAndProps, RecoverRejectedPieces, OverlayPavedSurfaces, ChargeNetConstruction, SelectAsOneThing,
  ConfirmBulldoze) — they showed raw property names in Options.

## UX

Review gets a "Park stats" fold (open by default, after issues and breakdown, before the permanent-effects box): a
"Keep within vanilla range" check, then one card per stat — label, "In game" / "Shown only" tag, value, one-line
meaning, slider (vanilla range while kept, hard limits otherwise), reset, and a "How it's calculated" fold with the
formula lines and "Similar to: Winding Park (0.9 ha) 20 · …". A gentle warning appears when values are outside the
vanilla range. Not shown for parking, roads and industrial types. Mock: the host returns `parkStats` from the real
Core; `mock/tests/parkstats.spec.ts` covers suggest → override → clamp → range off → reset.

## Companion park building (approved, implemented)

What: per park build, one hidden 1-cell park building at the best road frontage, made from a runtime clone of the
vanilla Tiny Park (`PocketPark01`, fallbacks PocketPark02 / CityPark05 / CityPark01) whose Attraction, LeisureProvider,
ServiceCoverage, ServiceConsumption (upkeep; no electricity/water/garbage/telecom), Park (`m_AllowHomeless = false`)
carry the build's stats. With it leisure, park coverage (wellbeing), land value from attractiveness, tourist trips and
upkeep work like a vanilla park; attractiveness moves from the lot to the building (vanilla maintenance/terrain factors).

- Core: `Core/Build/ParkCompanion.cs` — `ParkPrefabKey` (quantised stats → stable name "Placemaker Park a14 l6 r4250
  c2000 m13 u11000[ b]", parse/round-trip), `ParkCompanionPlanner.Find` (road frontage along the outline, 8 m lot fully
  inside, clear of roads, our objects and paths, away from corners; NoRoad reason), `ParkStatsEstimator.WithCompanion`
  (Applied flags: all with companion, attractiveness only otherwise), `KeyOf`. Tests: `ParkCompanionTests`.
- Game: `Economy/ParkCompanionSystem.cs` — `ParkCompanionPrefabSystem` (PrefabUpdate before PrefabInitializeSystem;
  every name ever used is kept in `ModsData/Placemaker/park-companions.txt` and registered at startup so saves resolve
  them), `ParkCompanionSystem` (Modification2 before Buildings.InitializeSystem; parking-companion recipe: archetype
  entity, `Hidden`, PrefabRef, Transform, UpdateFrame, `PlacemakerMember {Auxiliary, ParkCompanion = 10}`; flat zone
  cleared; removes the lot's AttractivenessProvider and marks the receipt), `ParkCompanionCleanupSystem` (PreTool).
  Group removal deletes it with the build (member tag). `BuildService.RequestParkCompanion` picks the site after Apply;
  no frontage → build note "No road edge for the park building: only attractiveness applies." and the lot keeps it.
- Load (`GroupRegistrySystem.SyncParkStats`): setting off → companions removed, lot attractiveness back; companion with
  an unresolved prefab → removed and recreated from the receipt; lot provider only while there is no companion.
- Setting "Real park stats (companion building)" (`RealParkStats`, default on; off = previous behaviour).
- Review: `summary.parkStats.companion` = yes | noRoad | off; "In game" tags follow it; "No road edge: only
  attractiveness applies" note; footnote explains the hidden park building.

Risks (none verified in game yet):
1. Directly created buildings: same recipe as the parking companion, which is still EXPERIMENTAL/off by default
   because it crashed during PLT development. Ours keeps a real mesh (never mesh-less) but is otherwise as untested.
2. Road connection: RoadConnectionSystem must link the 1-cell lot's front (placed 0.5 m from the road edge). If it
   does not, the building shows "no road access" (icons of Hidden owners should be hidden) and pathfinding-based
   effects (leisure, coverage, land value) stay off; tourism still counts it.
3. Saves without the mod: the clone prefab is unknown → obsolete-prefab building; systems guard prefab lookups with
   HasComponent in the paths read, but not verified. Uninstall path: setting off + load once (removes companions),
   save, then uninstall. If `park-companions.txt` is lost, companions are recreated on load (old one removed first).
4. Park maintenance vehicles will be dispatched to it; budget/efficiency/district policies apply; it occupies one
   zone cell inside our outline (s19 zone guard already blocks zoning there).
5. Upkeep is now charged by the city budget (vanilla park rate); construction stays Placemaker's own price.
6. Quantisation: up to ±13 % on attractiveness/leisure above 20, 250-steps for range, 100/500 for capacity.

In-game checks:
- Build a park next to a road: log "park companion … requested" then "created"; the info view for park coverage and
  the building's coverage around it; tourism attractiveness rises; city services budget lists the park upkeep.
- Select/bulldoze the build: the companion goes with it (no orphan in Parks & Recreation).
- Save, quit, reload: companion keeps its prefab ("registered park companion prefab" lines at startup, no obsolete
  warnings); delete `park-companions.txt` and reload: it is recreated.
- Setting off + reload: companions removed, lot attractiveness back. Build without road frontage: Review note and
  build note, lot attractiveness only.
- Notifications: no "no road access" / electricity / water icons visible.
