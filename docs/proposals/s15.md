# s15 — playtest round: buildings, paint lag, greyed-out options, version mismatch

User feedback (they ran a build older than Block paint):
1. "Paint doesn't go past roads but it isn't aware of buildings … when it builds, it destroys the buildings."
2. "The lag is pretty bad when I'm painting — maybe 5 FPS."
3. "When I can't see options, I should see them greyed out."
4. "I can't click Block paint." (their UI file was newer than their DLL)

## 1. Buildings

### Why builds destroyed buildings (decompiled 1.6.2f1, RESEARCH-NOTES-ADDENDUM 63–66)

- Zoned (spawnable) buildings are `Overridable | DeleteOverridden`. A new net or physical area that overlaps one gives the
  *building* a `Game.Tools.Warning`; Apply then deletes it — exactly how vanilla roads demolish houses. Our park paths,
  parking aisles and lot areas did this. (Overridable props only hide themselves; surfaces are not physical.)
- New ground nets and physical areas also block the zone cells under them (and every cell behind a blocked one);
  `ZoneCheckSystem` then condemns a building whose lot cells are no longer zoned. Rezoning its cells does the same.
- Nothing in the planners knew about buildings except the add-ons (Occupancy) and Roads (RoadObstacles).

### The mechanism (no build ever touches a building lot)

| Layer | What | Where |
|---|---|---|
| Capture | Every building and building extension near the area: lot quad (BuildingData lot × 8 m) and, where it reaches past the lot, its collision footprint. Cap raised 1500 → 6000. | `Game/Selection/BuildingFootprints`, `Game/Preview/SiteCapture` |
| Plan | End of `Composer.Compose`: nets touching a lot (centre ± real half width + 0.5 m) dropped with their attached objects (indices remapped); objects touching a lot dropped (markers stay); surfaces, areas, terraform and paint cut around lots into CS2-acceptable pieces (1 m corridor instead of a hole); zoning quads touching a lot dropped. `ComposedPlan.Protected` keeps the polygons; Declutter re-checks objects after nudging them. | `Core/Build/SiteSafety`, `Core/Geometry/ObstacleCut` |
| Review | "N buildings are in the way. They are kept: nothing is built on their lots." (+ "N parts were left out or cut back…") | `Placemaker.Issue.BuildingsKept` / `BuildingsLeftOut` |
| Build | Before Apply: live buildings carrying `Warning` while our build holds the tool = buildings the game would delete. The work items touching them are excluded and the build retries (same loop as rejected pieces); if nothing can be matched the build stops (`Placemaker.Build.WouldDemolish`). The result notes "N existing buildings stood in the way…". | `Game/Build/BuildService.Protect` |
| Clearing | "Clear existing trees and props" skips objects standing on a building lot. | `BuildService.Owner` |

Roads: the Roads layer's own "avoid obstacles" option still decides whether the planner re-routes around buildings; the
safety pass drops whatever still touches a lot either way (a road can no longer demolish houses, even with the option off).

### Selection modes

- **Every mode** (Draw, Block, Roads/perimeter, Paint, Block paint): after each outline rebuild the buildings under the
  outline are read (object search tree, never per frame) and shaded red; a hint says "N buildings in the selection stay".
- **Plain Paint**: new option *Paint: keep off buildings* (Options → General, **default on**). On: building lots are cut out
  of the painted outline (an enclosed lot is opened with a 1 m corridor — CS2 areas cannot have holes), buildings near the
  brush are shaded red while painting, and painting only over buildings says so. Off = the legacy outline exactly; the
  build still keeps the buildings (decision: the outline is the player's choice, the safety is not optional).
- **Draw / Roads**: the outline is the player's, so it is not cut; the overlay shows the buildings it covers and the build
  keeps them.
- **Block paint**: unchanged (its "buildings" brush rule already never paints lots); its obstacle reading now also includes
  footprints past the lot and building extensions.

## 2. Paint lag

### What ran per frame while a stroke was held (before)

| Cost | Before | After |
|---|---|---|
| Outline rebuild (marching squares + 6 smoothing passes; Block paint: booleans + round offsets) **+ keep-off-roads** (corridor booleans against every nearby road) **+ attachment search + marker follow** — each with its own net query (search tree walk + lane buffer reads) | every 0.15 s while dragging (~7×/s), even when the mouse did not move. Measured Core part alone for a 300 m painted area next to a 60-piece street grid: **65 ms per rebuild ≈ 450 ms of every second** (`PerfPaintTests.Outline_rebuild_with_road_clip_measured`), plus the ECS net queries (×3) and the fill-mesh rebuilds of the selection/clipped layers on every rebuild | **once on mouse-up** (a single ~65 ms hitch on that big case, typically a few ms) |
| Input revision | bumped every frame while the button was held (stamp or not) → state rebuilt every frame | bumped only when the stamp changed cells |
| Readiness checks (`CheckReady` of every step) | recomputed every frame (input revision changed) | skipped during a stroke |
| State JSON (hints, stage facts, readiness, ~2–4 KB) | built and pushed every frame | ≤ 10×/s while painting; the stroke end pushes at once |
| Stale outline fills | redrawn | hidden during the stroke (the painted cells are drawn) |
| Net query per outline rebuild | 3 identical queries | cached within a frame |
| BrushMask stamping + overlay boundary | 0.03–0.1 ms/frame (60–150 m brush), 2 ms/frame for the 1000 m brush | unchanged (already incremental; measured) |

Budgets in `Tests/Placemaker.Tests/PerfPaintTests.cs` (scaled by `TimingBudget`): 200 stamps on a 300 m area < 150 ms;
stamping + overlay boundary < 2 ms/frame; 1000 m brush < 25 ms/frame; Paint outline < 150 ms; Block paint outline < 400 ms;
cutting 36 lots out of an outline < 300 ms; full rebuild with road clip < 500 ms.

Expected in game: painting should not drop the frame rate noticeably any more; the remaining per-frame work is the stamp
(≪ 1 ms), the boundary lines of the painted cells, and a state push every 6th frame.

Not changed: Draw mode still rebuilds its outline ~7×/s while a corner is dragged (same pipeline) — it was not reported;
if it shows, the same deferral applies.

## 3. Disabled with reason

### Contract (additive)

C# `ControlSchema` / UI `Control`:
- `VisibleWhen` keeps its syntax but now means "applies when": the UI shows a non-applying control **greyed out** with a
  reason instead of hiding it. Older UIs keep hiding it.
- `HideWhenOff` (`hideWhenOff`): the exception — hide while `VisibleWhen` is false.
- `EnabledWhen` (`enabledWhen`): extra condition for being enabled (shown greyed otherwise).
- `DisabledReasonKey` (`disabledReason`): localisation key of the reason; absent → the UI words it from the condition:
  "Only when Lake is on", "Only when Layout is Alley or Grid", "Not when Fence is None".

Area-dependent availability (the outline, not other values):
- `IHasAvailability.Unavailable(AreaInput, List<Unavailable>)` (optional, per layer): control id or `feature:<layer>` → reason
  key + args ("Needs a street edge"). **s14's street-shops controls should adopt this** (no UI code needed).
- Built in: a feature whose layer's `MinArea` exceeds the whole selection → "Needs a bigger area (at least N m²)".
- Computed by `Core/Tool/Availability.For` when the inputs change (never during a stroke), sent with the design:
  `StepView.disabled: Record<controlId, LocText>`, `FeatureView.disabled?: LocText`.

UI (`lib/schema.controlAvailability`, `Controls.tsx`, `DesignStage.tsx`): greyed rows have `data-disabled`, `data-reason`,
40 % opacity, an editor that takes no input, and the reason first in the label tooltip. A greyed feature's switch cannot be
turned on (an enabled one can still be turned off). Summaries ("90° · 6 m") list only controls that apply.

### Every place that hid things, and what it does now

| Place | Now |
|---|---|
| Control `visibleWhen` (≈ 210 controls: `.When(...)` in the layers, Parking's lamp/median/angle options, Roads' cul-de-sac / avenue / grid-count options…) | greyed with a worded reason |
| Roads per-pattern essentials (`pattern=…`, 37 controls) | **still hidden** (`HideWhenOff`): greyed they would bury the 3–4 that apply to the chosen pattern; the pattern choice itself is the visible switch |
| Brush angle (only for the square brush) | always shown, greyed for the round brush: "Only for the square brush" |
| Block paint "Rules" row (only in Block paint) | also shown in Paint, greyed: "Only for Block paint. Paint keeps off buildings (Options)." |
| Area mode buttons | greyed with a reason when the DLL does not offer the mode (`state.areaModes`) |
| Features | were never hidden; now greyed with the area reason when they cannot fit |
| Feature options while the feature is off | unchanged (they fold under the feature's switch, which is visible) |
| Anarchy toggle (only with the Anarchy mod installed) | unchanged: hidden — it controls another mod |
| Generic markers control when the step declares typed entrances | unchanged: replaced by the Entrances section |
| Make row: mixes / feature variants are loadable by id but not listed | unchanged (they are not "options that don't apply") |

## 4. Block paint button / UI–DLL mismatch

- The game reloads `Placemaker.mjs` from disk but loads the DLL only at start, so after an update the two can disagree
  until a restart (the user's case: a UI with Block paint, a DLL without — `setAreaMode("blockPaint")` failed to parse and
  nothing happened).
- `PROTOCOL = 15` in `UI/src/contract.ts` and `UiModels.Protocol` in C# (a unit test checks they match); C# sends
  `state.protocol`. Different or absent → an amber line under the stage bar: "Restart the game: Placemaker's files were
  updated while it was running."
- C# sends `state.areaModes` (every mode it handles, `enabled`, `reason`). The UI greys a mode that is missing or disabled,
  with the reason. A DLL older than s15 sends no list: Block paint shipped together with the brush rules (s11), so
  without `brush.rules` its button is greyed with "Restart the game to use this…".

## 5. Brush cursor outside the Area stage (lead report)

After painting and moving on to Design (or while placing entrances) the big brush circle kept following the mouse:
the overlay drew it in every stage, and the brush still took strokes there. Now `Core/Tool/BrushCursor.Live`
(unit-tested) decides: tool active, Area stage, Paint / Block paint, not placing markers, mouse over the world (not over
the panel) — or a stroke still running (it always finishes on mouse-up). Only then does the tool run the brush input,
and only then does the overlay draw the brush cursor, Block paint's obstacle shading and its hover-block outline. The
brush hints are left out of the other stages too. The painted outline itself stays visible in every stage.
